Task 5: Running and reimplementing Logic-LM
Bharat Marimuthu, AIEA Lab (Faithful NeSy Reasoning)
Code and results: https://github.com/bharatmarimuthu/aiea-task5

I chose Logic-LM (Pan et al., Findings of EMNLP 2023). It has an LLM translate a natural-language problem into a symbolic program, and a solver then computes the answer. A self-refinement step feeds solver errors back to the LLM so it can fix the program. My work had two parts. First I ran the authors' code. Then I reimplemented the method on the gym-exercise Prolog knowledge base from Task 4.

Getting the authors' code (github.com/teacherpeterpan/Logic-LLM) running took some adjustment. Their requirements pin 2023 versions of torch and CUDA that would not install on my Mac with Python 3.14. Their Pyke logic-programming solver imports the imp module, which was removed in Python 3.12. I made a Python 3.10 conda environment and installed only what the solvers need: Pyke, python-constraint, z3-solver and a few utilities. Generating new programs was not possible because the code calls OpenAI models through the old openai 0.27 interface, and those models have been retired. The authors did publish the programs GPT-4 generated, though, so I could run the solver and evaluation half of their pipeline without an API key. For ProntoQA, ProofWriter, LogicalDeduction and AR-LSAT, my execution rates and execution accuracies match Table 3 of the paper. For example, ProntoQA ran 100% of its programs with 83.2% accuracy, and AR-LSAT ran 32.6% with 60.0% accuracy on those. I skipped FOLIO because it needs the Prover9 binary, which I did not compile.

For the reimplementation I kept the paper's stages and prompt format but replaced Pyke with SWI-Prolog, called from Python through the Janus bridge. Janus raised errors on unbound named variables, so the solver passes the LLM's query to Prolog as a string and parses it there. The solver also blocks unsafe predicates such as shell and assert, uses a five-second time limit, and returns short error messages for self-refinement. The LLM client uses the OpenAI-compatible interface, so it can point at a local model or an API. I used llama3.2 through Ollama. Ollama has to be installed as the app (brew install --cask ollama), because the Homebrew formula compiles LLVM from source on macOS 14 and takes hours. llama3.2 at first copied the first few-shot example for every question. Sending the examples as separate chat turns, not as one long message, fixed this.

I tested on 14 questions about the Task 4 knowledge base, with gold answers produced by running reference queries in Prolog. Three checks came before using an LLM: a solver self-test with valid queries, a typo, a syntax error and a blocked command; generating the gold answers; and an oracle run where the reference queries stand in for the LLM, which scored 14 of 14. With llama3.2 at temperature 0, Logic-LM answered 10 of 14 correctly, compared with 6 for direct prompting and 4 for chain-of-thought. Reruns gave identical results. Self-refinement raised the share of programs that ran from 93% to 100%. Logic-LM got all nine easier questions right but only one of the five harder ones. All four of its errors were programs that ran but meant something other than the question: a dropped condition, an extra condition, a misplaced negation, and a mix of "and" and "or" without parentheses. Two correct answers were right only by chance, from queries with swapped arguments that matched nothing when the gold answer was false. Chain-of-thought did worse than direct prompting, mostly because llama3.2 sometimes started writing Prolog and repeated it until the token limit. These results come from one small model and a small question set, but they show where the method is fragile. The solver guarantees that the answer follows from the program, but nothing checks that the program means what the question asked. That faithfulness gap is the focus of the Faithful NeSy Reasoning team.
